# xplace 4 卡实验结果（当前长度准入 V8 起见 §12；S1b–S6、V2–V7 为全量预留的历史结果）

## 0. 用户 guideline（2026-11-02/03/04）

1. A/B 效果都要有，并有消融：
   - A：跨模型迁移降低 Code TTFT；
   - B：cost-aware placement 降低 Conv 的性能下降。
2. Conv 相对同 trace 的 `no_move` 退化 ≤20%。主指标是 Conv avg TPOT，同时报告 P95/P99 TPOT 和 Conv TTFT。
3. 数据集：Code 用 SWE-smith ≥100K、输出 64；Conv 用 OpenThoughts3 bank256，保持原始长度。
4. 真实实验尽量少，最终结果来自真实实验。每个实验 ≤1h（以后每轮 ≤20 分钟），多个实验打包进同一个作业。
5. 分时（Code 驻留期间暂停 Conv）作为新增策略维度（11-03 同意）。
6. S6 之后继续分析并优化算法（11-04）。
7. serving 系统不能假设已知输出长度，准入按当前长度；实验负载要让长请求按当前长度也进不来；KV 不够时由 vLLM retract；placement 给请求预留增长空间，但不能假设已知完整输出长度；在这个设定下重跑所有 baseline 和本文系统（11-04）。

> **适用范围（11-04 晚补充）**：V1–V7 中所有受控策略（`no_move*`、`mig_random*`、`ca_*`）在准入时都按 prompt + max_tokens 预留，而 max_tokens 是回放的真实输出长度，相当于 oracle；planner 的剩余长度和挑选顺序也用了它。这些结果只作历史参考。V7 的 `kvcached_native` 不依赖输出长度。按当前长度准入的结果见 §12，从 V8 起。

## 1. 结论（S1b–S6，seed 702，1000s trace）

所有结论来自同一节点 d1n41a15g02（探针 12.6–12.7ms，与 pilot 节点同速），同一 trace（seed 702，1000s；4 个约 100K 的 Code，73 个 Conv），评估窗口 [300, 1000)。每轮 n = 4 个 Code、49 个 Conv。CI 是请求级配对 bootstrap，不包含 run-to-run 噪声。

| 结论 | 结果 | 证据 |
|---|---|---|
| **A 成立** | 迁移让 Code TTFT 降 45–53% | 同一作业配对：`no_move` → `ca_full` −44.6% [−69.4, −7.2]；跨作业：`no_move` → `mig_random` −49 ~ −54%；对公平基线 `no_move_fair`：−38 ~ −40%，且后者的 Conv TTFT p99 达 79s |
| **分时成立，是最大的杠杆** | Conv TPOT 降 26–30%，Code TTFT 降 50–55% | 同一作业配对：`ca_full` → `ca_full_tm` −28.2% / −55.2%；`no_move` → `no_move_tm` −30.3% / −53.0% |
| **组合效果** | `no_move` → `ca_full_tm`：Code TTFT −74 ~ −76%，Conv TPOT −27 ~ −31% | 跨作业，同一节点，两次独立的 `no_move` |
| **Conv 退化 ≤20%** | 满足：所有迁移策略的 Conv TPOT 都不差于 `no_move`（−31% 到 −1%） | 表 2 |
| **B 的机制成立，端到端测不出** | cost-aware placement 消除了大部分可避免的档位跨越；但它对 Conv TPOT 的作用（≤2.5%）小于干扰噪声（约 ±12%） | §3 |
| **分时下的 B** | 无差别：`mig_random_tm` 与 `ca_full_tm` 都是 26.2–26.8s / 22.26ms | S6 对 S1b |
| **正确性** | 12 个 trial 全部 77/77 输出长度精确；55 次迁移全部逐字节校验通过；没有 MemoryError；持有期间 Conv 一个 token 都没出 | 表 2 |

**分时的代价**：几乎每个 Conv 都会碰上一次约 25s 的停顿（最大 token 间隔 p50 为 25s）；Conv TTFT 均值从 1.4–1.8s 升到 3.6–4.6s，p99 约 28s；Conv SLO 达成率（TTFT ≤5s 且 TPOT ≤50ms）从 0.86–0.96 降到 0.78–0.80。如果 SLO 对停顿敏感，应使用不开分时的 `ca_full`。

## 3. 机制：Conv TPOT 拆分与 B

| 策略（作业） | 无 Code 时段 | Code prefill 期间 | Code decode 期间 | 持有停顿 | 无 Code 时段步时 | G16 占比（可避免） |
|---|---|---|---|---|---|---|
| `no_move`（S2 / S3） | 21.10 / 20.40 | 8.32 / 7.83 | 2.79 / 2.41 | — | 22.21 / 21.75 | 0.37（0.17） / 0.26 |
| `mig_random`（S4） | 20.85 | 6.77 | 2.53 | — | 23.05 | 0.54（0.41） |
| `ca_full`（S1b / S3 / S4） | 20.54 / 20.24 / 20.47 | 7.96 / 7.45 / 7.84 | 2.5–2.6 | — | 22.09–22.37 | 0.28–0.41（0.07–0.13） |
| `ca_return`（S5） | 19.65 | 5.92 | 2.32 | — | 21.47 | 0.11（0.04） |
| `ca_full_tm`（S1b） | 19.99 | 0.15 | 0 | 2.11 | 20.42 | 0.00 |

（单位 ms。可避免的 G16 = Conv 总数 ≤32、本可全部留在 8 档，却有 rank 进了 16 档的时间占比。）

- **B 的机制**：
  - 不考虑代价的迁移造成档位跨越：`mig_random` 的可避免 G16 占比为 0.41，无 Code 时段步时比 `no_move` 高约 4.9%；
  - cost-aware 版本把可避免 G16 压到 0.04–0.13，无 Code 时段步时回到 `no_move` 的水平；
  - 起主要作用的是 cost-aware 回迁（`ca_return` 0.04）。
- **端到端测不出 B 的原因**：Code 驻留期间的干扰贡献在各轮之间波动 5.9–8.3ms（约 ±12%），取决于每个 Code episode 落进轻模式（Conv 约 70–130ms/token，Code prefill 约 50s）还是重模式（200–390ms，约 60s）。S4 的同机配对中，`ca_full` 比 `mig_random` 高 2.4% [+1.2, +3.8]；拆开看，无 Code 时段 `ca_full` 好 0.38ms，Code prefill 期间差 1.07ms（`mig_random` 4 次中 3 次是轻模式）。
- **simulator**：在所有区间（λ 0.05–0.12，开或不开分时）placement 本身的 B 都 ≤2.5%。
- **低置信度观察**（只作后续方向）：
  - 随机准入的两轮 Code prefill 偏短（51–52s，其他 55–60s），轻模式比例 5/9 对 8/31，p≈0.12；
  - 40 个 episode 中，每 rank 最大 Conv 数 ≥10 时轻模式占 8/12，<10 时占 5/28；
  - 但 Job 1c 的受控实验在均衡布局下显示过相反趋势，因果关系未确认。

## 4. 与预注册预测对照（`forecast-short-s702-v2.json`，S1b 前生成）

- **落在区间内**：`no_move`、`ca_full`（三次）、`ca_full_tm`、`no_move_fair` 的 Code TTFT 和 Conv TPOT；`mig_random_tm` 的 Conv TPOT。
- **偏离**：
  - `no_move_tm` 的 Code TTFT：实测 53.4s，预测 29.1s；live 中有一个 Code 排队 93s，单卡碎片比 simulator 严重；
  - `mig_random` / `ca_admit` / `ca_return` 的 Conv TPOT 低于区间：这几轮的干扰偏轻；
  - 所有 Conv TTFT 都高于预测：simulator 没有建模控制面延迟，v2 针对这一点。
- **B 的预测**（`ca_full` 对 `mig_random` −5.5%）没有在 live 中复现。

## 5. 局限

- 单 seed、单节点；每轮只有 4 个 Code，Code TTFT 的 CI 很宽。跨作业比较虽在同一节点，仍受干扰模式噪声影响。
- 干扰的两种模式机制不明（两个进程在同一组 GPU 上 time-slicing，加上 EP collective）；没有测试 MPS。
- 控制面阻塞使 Conv TTFT 偏高，v2 修复，见 §6。

## 6. 算法优化 v2：控制面（V2 = 286379，850s trace，5 轮同机配对）

**改动**（详见 protocol §7）：
- Conv 准入快路径：缓存 Code 视图，用 epoch 保证只会高估 Code 占用；
- 分时下先停 Conv 再准入 Code。

两项都只改控制面，不改 planner。

## 11. kvcached 原生基线（V7 = 288709，seed 704，850s，4 轮同机配对）

设计与预注册见 protocol §13。节点 d1n41a18g02，探针 12.8ms；之前的作业都在 d1n41a15g02，探针 12.6–12.7ms。原始数据在 `evidence/xplace-v7-native-20261104/job-288709`（SHA `ba0535f5…`），报告见同目录 `report.md`。

### 11.1 原生基线怎么做

- **`kvcached_native`**：请求到达即交给 vLLM（不指定 DP rank）。控制器不准入、不排队、不迁移、不暂停。调度器切换到 vLLM 原生准入：按步分配 KV，显存不够时抢占并重算。
- **容量对齐**：原生轮开始前，在每张卡上占掉多余显存，使 kvcached 可映射的共享 KV 为 170 个 96 MiB 页组（15.94 GiB），与受控预算相同。实测四卡为 16.006/16.006/16.008/15.984 GiB（取整到页组）。原生轮结束后释放，容量恢复到 35.8–38.3 GiB。
- **激活内存**：原生轮中 Code prefill 的激活内存会占用剩余显存。每 60s 采样的可映射容量最低为 15.42–15.95 GiB，即至多少约 0.5 GiB。受控轮的激活不计入 16 GiB 预算，所以原生基线在容量上略吃亏。

### 11.3 结论

- **原生按需分配在这个负载下没有"单卡放不下"的问题。**
  - 4 个 Code 都是到达即进入：提交延迟不超过 2ms，KV 在 2.7–5.6s 内开始增长。TTFT 48–60s 基本就是两个模型并行时的 prefill 时间。
  - vLLM 原生 DP 负载均衡把 4 个 Code 依次分到 rank 0–3。到达时所在卡的已映射 KV 为 1.41、3.38、6.19、6.66 GiB。
  - 余量很薄：后两个 Code 的峰值为 15.84、15.75 GiB，距上限 15.94 GiB 只剩 0.1–0.2 GiB。负载再重一点就会开始抢占和重算。
  - 全程 0 次抢占，kvcached 分配未命中 0 次。
- **碎片是全量预留造成的。** 按"输入 + 输出"全量预留时，`no_move_v2` 的后两个 Code 在控制器里排队 212.8s、110.2s。Conv 的实际占用约为预留的一半，所以原生方式放得下。
- **相对原生，迁移没有 A 收益；收益全部来自分时。**
  - `ca_full_v2` 用 16 次迁移追平了原生（Code TTFT +0.5%），控制器准入路径和迁移暂停还让 Conv TTFT 翻倍（0.25 → 0.51s）；
  - 加上分时与按需切片后，Code TTFT −49%，Conv TPOT −24%。
- **原生的 Conv TPOT 比全量预留高 12.8%**：Code 一到就与 Conv 并行，驻留时间占比 0.39 对 0.24，Conv 受干扰的时间更长。这与 V6 中"不分时的迁移让 Conv 变慢"是同一机制。
- **placement 的 B 在原生下没有空间**：原生 DP 负载均衡已把可避免的 G16 占比降到 0.02，与 `ca_full_v2` 相同；两者无 Code 时段步时为 21.57 对 21.44ms。
- **复现**：`ca_full_tm_slo` 为 27.7s / 23.60ms，与 V6（27.7s / 23.6ms）相同，且换了节点。

### 11.4 对研究叙事的影响（待用户决定）

- A（迁移降低 Code TTFT）只相对全量预留成立。论文若以 kvcached 原生为外部基线，迁移的作用需要重新定位：
  - 分时要求驻留的 Code 已拿到完整 KV，否则切片时 Conv 增长会占掉 Code 未分配的页，Code 只能抢占自己，而 Conv 处于暂停中，形成死锁。这要求 Code 全量预留，但不要求 Conv 全量预留；
  - 因此可以有"只给长请求全量预留、Conv 按需分配"的变体。在这个负载下，Code 预计不迁移就能进入，迁移的作用只剩在更重负载下为 Code 腾出空间。
- 要让迁移在论文中成立，需要一个原生方式出现抢占或单卡放不下的负载区间，并证明迁移在那里有收益。

## 12. 当前长度准入（V8 起，进行中）

设定见 protocol §14–§15：受控策略准入时只预留 prompt + 256 token，之后按步增长，KV 不够时由 vLLM 抢占重算；planner 不读输出长度，按"decode 速率 × 时间窗口"给增长留余量；每轮用占位把物理容量对齐到 16 GiB/卡。负载为 Conv 0.12 RPS，Code 在 420/540/660/780s 到达，时长 900s，seed 911（按只依据 trace 的规则选出）。

### 12.1 V8（289203，d1n41a28g03，探针 12.6ms）的两个发现

**页共享使只迁走部分 Conv 腾不出空间**（第一轮 `ca_full_tm_slo`，`max_moves`=8）：
- 420s、540s 的 Code 直接准入，TTFT 31.8s、30.9s；
- 660s、780s 的 Code 迁移规划 172 次全部不可行，等 Conv 自然排空后才进入，TTFT 401s、313s；0 次抢占。
- 机制：按当前长度逐步增长时，kvcached 给单个块挑"最满但有空位"的页，同一 rank 上的 Conv 块交错在同一批 2 MiB 页里。Conv 结束后留下的空位会被其他 Conv 填上，页很少整页空出，所以 Conv 的映射量停在历史高点（rank 3 的 Conv 数从 13 降到 11，映射一直是 10.12 GiB）。Code 属于另一个模型，用不了这些空位。
- 当时的推断是：只有把一张 rank 上的 Conv 全部迁走才能腾出页，而 660s 时每 rank 有 13–14 个 Conv，大于 `max_moves`=8。
  - **后来更正**：V9c 发现，这一轮迁移被挡首先是因为物理空闲块检查（§12.3）。V10 修复后，准入在目标 rank 的 12–17 个 Conv 中迁走 2–13 个（中位 9 个）就够了，没有一次清空整张 rank。
  - 页共享的实际影响是要迁走大部分 Conv，其中 11/18 次超过 8 个，所以 `max_moves` 24 仍然需要。
- 旧设定下每个请求在准入时一次分配全部长度，基本独占自己的页，所以 V1–V7 的迁移是可行的。

**原生 DP 下被 KV 挡住的请求会让本实例空转，拖垮共址实例**（原生轮）：
- 660s、780s 的 Code 按当前长度放不进，在 vLLM 内部排队，到 1900s 截止都没开始；
- 1900s 时只完成 38/109 个请求，986–1872s 间只完成 6 个，Conv 约 350ms/token；全程 0 次抢占。
- 机制（vLLM `DPEngineCoreProc.run_busy_loop`）：本地有未完成请求（包括调度不上的排队请求）时，引擎每轮都执行 dummy batch；只要有一个 rank 有排队请求，DP wave 就不停。于是 Code 实例的 4 个 rank 一直空跑 EP 前向、干扰 Conv；Conv 变慢后 KV 释放更慢，Code 更进不来，形成正反馈。
- 受控策略在控制器侧排队，放得下才把 Code 交给 vLLM，不会出现这种空转。这是"在控制器侧做准入"的一个直接理由。

样本：单节点、单 seed、各 1 轮。

### 12.5 结论（seed 911，单节点，每策略 1 轮）

- **问题在当前长度准入下更严重。**
  - 原生 vLLM DP 下，660s、780s 的 Code 放不进，在 vLLM 内部排队，还让 Code 实例空转、拖垮 Conv。到 1900s 只完成 33/109，V8 为 38/109。
  - 控制器侧排队（`no_move_v2`）消除了空转，Conv TPOT −90%，但这两个 Code 仍要排队约 400s。
- **A（迁移降低 Code TTFT）成立。**
  - 迁走目标 rank 上的大部分 Conv 后，660s 的 Code 只排队 0.7–1.5s，不迁移时为 297–415s；
    - 18 次准入迁移，在目标 rank 的 12–17 个 Conv 中迁走 2–13 个（中位 9 个），没有一次清空整张 rank；
    - 其中 11 次超过 8 个，即 V8 时的 `max_moves` 上限。页共享下迁走的 Conv 少了腾不出整页；planner 只计入所有者全部被迁走的页。
  - Code TTFT 在并行下 −76%，分时下 −87%；
  - 代价是 Code 更早驻留、与 Conv 并行更久（驻留占比 0.31 → 0.63–0.65）。Conv TPOT 在并行下 +33~39%，超出 20% 的上限；分时下 +10~25%。
- **分时解决 Conv 的代价。** 在不迁移、随机、代价感知三种 placement 上：
  - Code TTFT 分别 −24%、−59%、−60%，Conv TPOT 分别 −15%、−24%、−30%；
  - 代价是 Conv TTFT 变长（p99 约 24s），需要按需切片补回。
- **最终策略 `ca_full_tm_slo` 对 `no_move_v2`**：Code TTFT −88.5%，Conv TPOT −4.6%（不但没变差，还略有改善），Conv SLO 1.00，0 次抢占。
- **B（代价感知 placement）成立，全部来自回迁。**
  - 不分时 −4.3%，分时 −11.6%；代价感知准入几乎为零（−0.8%，在回迁之上加是 +0.1%）。
  - 准入没有作用的原因：页共享下要迁走目标 rank 上的大部分 Conv，迁哪些请求基本已经定了。`ca_admit_v2` 与 `mig_random_v2` 选的是同一张 rank（15 个 Conv），都迁 9 个，只有目的地不同。
  - B 的来源不在 CUDA graph 档位：这个负载下每个 rank 超过 8 个 Conv，16 档不可避免。来源是最满 rank 的 batch 和 attention 长度：随机迁移从一张 rank 迁走大部分 Conv 后不回迁，Conv 长期失衡，无 Code 时段各 rank 的 Conv 数差为 7.2（代价感知为 2.1）。
  - 分时下 780s 的 Code 也走迁移准入（不分时的随机迁移中它直接准入），随机迁移迁走 22 个 Conv（不分时 9 个），之后的回迁更重要，所以 B 更大。
- **按需切片**：
  - 对全程分时，Conv TTFT −75%，Conv SLO 0.79 → 1.00，代价是 Code TTFT +16%；
  - 对周期切片，Code TTFT −8%。
- **增长余量（负结果）**：
  - 留与不留余量都没有抢占，差别很小且方向不一：不分时 +3.3%，分时 −0.8%；
  - 页共享下 Conv 增长先填已映射的空位，实际增长比"速率 × 窗口"小；
  - 在这个负载下，余量是不必要的保守。
- **公平门**：在控制器里让 Code 优先，Code TTFT −13%（不显著），却把 Conv TTFT 拉长 126 倍。它不能解决单卡放不下的问题。
- **simulator 预测**：
  - 迁移策略的 Code TTFT 偏差约 ±5%；
  - Conv TPOT 系统性低估 2–4%，`mig_random_tm_v2` 低估 7%；
  - 不迁移策略的 Code TTFT 取决于 Conv 自然排空，偏差为 −7% 到 −16%；
  - 预测中随机迁移会触发 3–4 次抢占，实测为 0；
  - simulator 的页共享模型是"高水位"：只要一张 rank 上还有 Conv，它的页就不减少。所以在模拟中，每次准入都要迁走目标 rank 上的全部 Conv（13–17 个），实测为 2–13 个（中位 9 个）。准入次数也有出入，所以总迁移数有多有少。
