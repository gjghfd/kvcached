# EP4TP2 组件诊断预检

## 结论

r9 是本地候选，不是已部署实验。它绑定新增诊断模块、571 项启动身份及新的 deployment manifest；训练请求、预算、采样周期、截止数值和科学阈值不变。GPU 提交仍由 `HOLD` 阻止：还须完成逐轮组件诊断验收工具及独立分析协议绑定。

r8 两个顺序的负结果不变：176 条请求全部保留，覆盖率 78.77%–86.78%，最差 Code TTFT 采集开销 +17.77%。本预检不重算这些指标，不构成实测代价、正式消融或混合拓扑验收。

## CPU 启动超时

原始本地回归的 570 通过、1 次 5s 子进程超时保留。新增一次有界诊断回归，571 项通过；两个最小子进程的 `Popen` 约 6.5/6.7ms，调用约 45ms。仅当子进程存活超过 500ms 才采集进程状态及栈，本次未触发。

这说明超时未在该次原顺序回归中复现，不证明原故障根因已解决。未修改 `causal_job.py`、原测试或 5s 时限。新候选另做一次不带观测插件的本地完整测试和一次上传目录完整测试，均为 **571 通过**；不能用成功结果覆盖首次失败。

## 保留容量

读取两个顺序全部 8 份 collection，仅核验容量，原文件 SHA 不变。实际保留量按紧凑事件 JSON 计算，不能把格式化输出文件大小当成 512MiB 保留上限。

- 通用 API 压力界限假设每组件 16 个长阶段名：按原失败比例估计均可容纳，但假设每轮失败时，4 个 c16 case 超出上限，最大 **572.70MiB**。该失败保留。
- 冻结生产路径的 AST 核验得到 scheduler 每次最多 3 个阶段，execution/batch-link 每次最多 9 个阶段，合计 4+12+12 个组件。固定原始事件体量，再给每轮加满 64KiB 部分结果，最大估计 **483.30MiB**，余量 **28.70MiB**。
- 两种估计均未改变 16 阶段、64KiB 部分结果和 512MiB 总上限。细化结果依赖当前源码路径及明确字段长度假设，不保证未来更高 token 产出仍可容纳；GPU 验收仍要求采集中零事件丢失，迟到/部分结果不得成为有效预测输入。
