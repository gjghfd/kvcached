# r9 RPC 时间线：截止取消已解释，超时根因仍未证明

本次只分析318110已取回的冻结数据，不重跑原验收、不访问集群、不修改运行代码或科学门槛。四个case的37,828个scheduler调用全部进入新诊断；取消和缺失快照没有填值，也没有从分母删除。

## 时间绑定与缺失

30,780次调用记录完成，其中30,718次可将客户端`rpc_started`、生产端`placement_snapshot.observed_at`、客户端`available_at`和结束时间按同一时钟及rank绑定。另62次已完成调用的快照因64KiB部分结果上限省略，两个c16 case各31次；它们保持“完成但无法绑定生产时间”。

## 成功且保留快照的条件分布

仅在上述30,718次调用中，客户端开始到生产时间戳的中位数为3.82ms、p95为41.06ms；生产时间戳到客户端可用的中位数为1.86ms、p95为4.31ms。整个客户端RPC区间中位数为7.09ms、p95为50.35ms。不同区间的中位数不能相加。

这些是成功子集的描述，不是全部调用的延迟分布。case间也不一致：train-c16-r0的生产时间戳后区间p95为23.11ms，其他case约2.79–3.72ms，不能只用总体p95掩盖该差异。

- 时间戳前区间包含客户端派发、IPC、engine派发及生产方法打点前的工作，不能等同于生产端排队。
- 时间戳后区间包含快照构造、wrapper记账、返回传输和客户端调度，不能等同于序列化或网络开销。
- 取消调用的客户端生命周期最大1.602s；其中49次超过1s。该时间包括等待和取消传播，现有记录不能区分事件循环迟滞与取消收尾，也不能据此认定GPU阻塞。

因此，既不能由成功子集推断7,048次取消的生产时间，也不能把这些区间解释为Code TTFT的因果来源。

## tick2410不是deadline超时

train-c4-r1的tick2410仍是不完整轮：`cancelled=true`、`error_type=CancelledError`，完成记录距离80ms deadline尚有67.43ms。trace cutoff发生在该轮执行期间；事件顺序为`trace_cutoff`(42662) → `sample`(42663) → `collection_stop`(42664)。

冻结代码的`trace_runner`先记录cutoff，再调用`CausalCollection.stop()`取消采样任务。17项本地诊断测试全部通过，其中直接调用冻结收集器的合成测试复现了“28个组件均及时完成，但父轮次被stop取消，聚合结果仍不可用”的路径。这解释该轮的不完整标记；不是需要放宽deadline或修补为完整的错误。原验收、覆盖率及截断记录不变。

## 修复边界与下一步

目前只解释了上述取消边界，未证明主要RPC超时根因。不提交原包补跑，也不只为凑齐反序块占用新allocation。

下一修订先补齐测量边界：用有界关联标识区分客户端派发、生产端进入/退出、返回可用与事件循环迟滞，并在RPC取消后仍保留独立的生产端诊断；成功调用的紧凑时间元数据不应依赖保留整个部分快照。先做本地取消、迟到、身份绑定及预算测试，再冻结新修订。现有80ms/100ms、64KiB/512MiB、CPU子进程5s及工作负载不变；新增诊断的开销仍须独立配对验收。

r9原结果继续拒绝：活跃完整率70.51–76.91%低于90%，仅4/8配对，三个描述性中位损失超过5%；88请求中19完成、69截断。四项campaign科学门槛均未通过，不启动混合拓扑。
