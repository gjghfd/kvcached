# r9 组件诊断：一次性启动保护

## 适用范围

本轮只允许一个 r9 block0 诊断作业，单节点 4 张 A800、最长 1h。它用于定位失败采样轮次中被组合返回掩盖的组件阶段，不是正式效果验证。r8 两顺序的科学拒绝、原 CPU 子进程超时和容量压力估算超限仍保留；新诊断开销尚无 GPU 结论。

GPU 包、80ms 截止、100ms 周期、64KiB 部分结果、512MiB 总容量、trace、seed、物理预算、并发和原始输出长度均不变。新启动保护不加入 GPU 包，启动测试仍为 571 项；本地保护测试为另行验证的 55 项。未放宽预测或性能门槛，不与 r8 跨版本配对。

## 保护与验证

- 逐 SHA 校验冻结候选、归档、分析、启动许可和 189 个 PAUSE；HOLD 保留，另以新许可记录完成的预检条件。
- 新远端 tag 必须原先不存在；传输后核对归档 SHA、清单 SHA 和各文件 SHA。失败目录、意图和输出保留，不覆盖或自动重传。
- 提交前检查查询下限，重新核对包与 HOLD；原子创建本地和远端一次性锁。一次 sacct 验证两个旧作业 COMPLETED/0:0，一次 squeue 确认空队列，才允许一次 sbatch。
- 队列非空、会计失败/缺失/重复、SHA 改变、重复调用、超时或不确定提交回执均不能触发自动重试。提交后不立即轮询；没有实际 Start 就不设置结束提醒。

55 项 CPU 测试覆盖真实 tar/SHA、模拟 Slurm 命令、环境与资源限制、忙队列、会计异常、重复部署/提交、接收后回执丢失、超时、本地并发锁、精确查询边界，以及真实冻结包的只读绑定和篡改拒绝。未在登录节点运行 Python、测试或推理。

证据根目录：`evidence/ep4-tp2-ablation-20261111/component-launch-20261112-r0/`。`guard-tests-r1.json`/XML 保存 55 项结果；`readiness-r0.json` 绑定保护源码、测试、分析与旧风险，`readiness-verification-r0.json` 保存实际绑定核验。远端动作的唯一回执位于 `evidence/xplace-staging/ep4-tp2-component-diagnostics-20261112-r9/`，作业状态以这些回执及随后不早于查询下限的 Slurm 观测为准，不能从本地许可推断已提交或完成。

## 本轮实测结果与修复候选

部署没有完成。远端于 11 月 12 日 23:29:10（北京时间）进入部署脚本；本地 240s 传输上限及 10s TERM 宽限耗尽后结束 SSH。23:34:40 在 ln02 的唯一只读核验确认：队列为空，313797/315554 均 COMPLETED/0:0；新 tag 仅有 940,032 字节归档和原 HOLD，没有上传目录、部署成功标记或提交锁。

该 940,032 字节的 SHA 与本地 1,655,236 字节归档的同长度前缀完全相同，尚缺 715,204 字节。这证实传输不完整，不证明网络/网关根因；也不能仅凭 ln02 的进程列表断言未知原登录节点上的写入者已全部退出。55 项本地保护测试不保证真实链路吞吐。失败文件、意图、完整 SSH 日志和锁均保留，未重传，也从未调用 sbatch。

`recovery_fence.py` 是尚未远端执行的隔离候选，14 项本地测试通过。它要求仍是已观测的精确部分文件、无发布/提交证据，将旧路径移至保留区并保存只读前缀快照；旧路径必须永久保持缺失，使延迟旧写入者即使补齐已打开的文件描述符，也不能通过原路径的 SHA 检查。测试覆盖延迟写入、重复调用、状态变化和符号链接拒绝。它不是完整恢复器，也不授权重传或提交。

下一步须补齐新归档路径、传输计时证据、独立提取/原子发布与新的提交绑定，并测试后再执行隔离；不得重建 `upload-r0.tar.gz` 远端旧路径、重放原部署、删除旧锁或放宽任何科学门槛。传输预算若修订，必须单独记录依据，不能改 CPU 的 5s、采样的 80ms/100ms 或 GPU allocation 的 1h 上限。
